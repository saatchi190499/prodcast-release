# Единый выпуск ProdCast

## Репозитории и права

Компоненты собираются в своих приватных репозиториях. Их workflow вызывает закреплённую по commit SHA процедуру `Collect component package` из этого репозитория. Она получает только артефакт `release-payload`, проверяет манифест, исходный commit, контрольные суммы и публикует пакет в черновик здесь. История приватного кода не копируется.

В App, Agent, AI и Worker нужен Actions secret **RELEASE_REPO_TOKEN** с доступом только к `saatchi190499/prodcast-release`, Contents: read/write. Нужен доступ аккаунта-владельца токена к этому репозиторию. Исходный `GITHUB_TOKEN` используется только для CI artifacts и GHCR. Клиентам токен не передаётся. В `prodcast-release` сборка/публикация использует собственный `GITHUB_TOKEN`.

У App есть отдельная ручная процедура `Distribute release publishing credential`: она шифрует уже существующий ключ публикации на публичные ключи Secrets API Agent/AI/Worker. Значение токена не выводится. Зашифрованные результаты устанавливаются администратором через Secrets API; для ротации повторяют ту же процедуру. При отсутствии ключа проверка доступа останавливает выпуск до сборки.

Можно дополнительно назначить required reviewers для environment `release-publication`. Независимо от этого публикация запускается отдельно вручную с явным подтверждением совместимости и ожидаемым SHA256 манифеста.

## 1. Подготовить черновик и собрать изменившиеся компоненты

Перед созданием тегов один раз запустите **Actions → Prepare release draft**, указав номер комплекта (например, `v0.5.0`). Дождитесь успешного завершения. Эта процедура последовательно создаёт один общий черновик; сборки компонентов сами черновики не создают. GitHub допускает несколько черновиков с одним тегом, поэтому одновременное создание из компонентов запрещено.

Создайте новые теги вида `v0.5.0-rc.1` на выбранных коммитах нужных компонентов. Все теги с базой `v0.5.0` направляют результат в общий черновик `v0.5.0`. Повторная сборка может использовать `v0.5.0-rc.2`; старые contributions остаются для прослеживаемости, а план явно выбирает нужный.

Каждый компонент добавляет два уникальных файла:

- `prodcast-<component>-<tag>-component.zip` — артефакты сборки без конфликтов имён;
- `prodcast-<component>-<tag>-component.json` — commit, версия, размер, SHA256 ZIP и исходного манифеста.

SHA256 descriptor выводится в Actions log. Одинаковые пакеты можно отправить повторно; замена существующего пакета другим содержимым запрещена. После появления `assembly-lock.json` новый вклад в этот черновик блокируется. Используйте новую версию для следующего комплекта.

Ручной запуск `Release packages` / `Release Windows package` в исходном репозитории проверяет только доступ; сборку запускает тег. Исторические теги сохраняют свои исторические workflow.

## 2. Зафиксировать состав

Скопируйте `plans/example.json` в файл с номером версии, заполните настоящие descriptor SHA256 и проведите review/merge плана. Пример не является готовым выпуском. `base.manifest_sha256` берётся из доверенного описания базового релиза и проверяется перед использованием любых его файлов.

`components` содержит только заменяемые компоненты: `app`, `agent`, `ai`, `worker`. Остальные компоненты и их бинарные файлы сохраняются из базового Complete. License намеренно нельзя пересобрать или заменить этой процедурой. Manager, офлайн-пакеты ОС/БД и внешние AI-компоненты наследуются из базы; их обновление требует отдельно подготовленной совместимой базы. Эта процедура не обновляет Manager и системные зависимости.

Нужен опубликованный базовый комплект с форматом Manager schema 3 (например, v0.4). Bootstrap с нуля без базы не поддерживается. Исходные пакеты приложений не изменяются; верхнеуровневые имена приводятся к версии комплекта, а исходные версии и отображение имён сохраняются в манифесте.

## 3. Собрать черновик

Запустите **Actions → Assemble complete release**, передав путь `plans/<version>.json`. Процедура:

- фиксирует план через `assembly-lock.json`;
- скачивает выбранные сборки и базовый Complete, сверяет SHA256;
- сохраняет Manager schema 3, изображения и сведения о совместимости версий;
- создаёт `ProdCast-<version>-complete.zip`, новый `release-manifest.json` и контрольные суммы;
- помещает результат в тот же черновик, не публикуя его.

После успешной сборки Complete workflow сохраняет все промежуточные `*-component.zip` и `*-component.json` (включая невыбранные RC) в GitHub Actions artifact `release-inputs-<version>` на **7 дней**. В копию также входят план сборки и список контрольных сумм удаляемых assets. Только после успешной загрузки этой копии и повторной сверки итоговых файлов дубликаты компонентов удаляются из Assets черновика.

В релизе остаются Complete ZIP, манифест, контрольные суммы, описание и отчёт проверки; небольшой `assembly-lock.json` сохраняется как служебная фиксация состава. При публикации добавляется подтверждение проверки. Неизвестные файлы, отдельные дополнительные пакеты и опубликованные релизы автоматическая очистка не затрагивает. При ошибке архивации или проверки очистка не начинается. Если удаление прервалось, копия доступна в Actions для разбора; Complete не пересобирают и не перезаписывают.

Правило выполняется только как продолжение новой успешной сборки. Уже готовый черновик v0.5.0 и предыдущие релизы остаются без изменений. По истечении 7 дней копия входных пакетов удаляется GitHub; полный комплект и происхождение выбранных компонентов в его манифесте остаются в релизе.

Неизменённый внешний Ollama ZIP не дублируется: в манифесте и описании остаётся ссылка на базовый релиз. Модель по-прежнему скачивается отдельно. Новая инструкция помечает унаследованное руководство базовой версии; фактические имена/версии берутся из нового манифеста.

При прерванной отправке пакета компонента можно повторить загрузку тех же байтов. Если сборка Complete прервалась после загрузки части итоговых файлов, автоматическая перезапись запрещена: сначала разберите состояние черновика и используйте новую версию. Опубликованные релизы никогда не изменяются.

## 4. Проверить и опубликовать

Получите draft Complete под аккаунтом с доступом к репозиторию. Проверьте установку/обновление через Manager на нужной площадке, совместимость App/Agent/Worker/AI и запишите область проверки. Структурные тесты сборщика подтверждают целостность и сохранение формата; они не заменяют установку на VM.

Запустите **Publish approved release**: версия, точный SHA256 `release-manifest.json`, результат/ссылка на проверку и checkbox подтверждения. Процедура повторно сверит ZIP и вложенный манифест, сохранит отдельный `publication-approval.json` и опубликует проверенные байты без пересборки. Манифест внутри ZIP сохраняет исходный статус сборки; факт и область последующего одобрения указаны в receipt и описании GitHub Release.

README ссылается на `/releases/latest`, поэтому после стабильной публикации клиент видит новый комплект без ручного обновления номера. RC-публикации не становятся Latest. Merge в main сам по себе не создаёт ни релиз, ни деплой.
