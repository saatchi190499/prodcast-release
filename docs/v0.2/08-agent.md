# 08. Agent — клиентский Windows-компьютер

Agent устанавливается под учётной записью пользователя приложения. Он выполняет разрешённые локальные workflow-блоки и notebook-команды; серверные расписания обслуживают отдельные Windows Workers. В v0.2 включён неизменённый установщик из `prodcast-agent/v2026.9.19-rc.1`, внутренний product version остаётся `2026.9.19.1`.

## 1. Подготовить рабочий компьютер

Проверить Windows x64, доступ к HTTPS App и синхронизацию времени. Получить публичный CA площадки от администратора, сверить fingerprint по независимому каналу и установить в доверенное хранилище по корпоративной процедуре. Приватный ключ CA, DB/Redis пароли и служебные ключи приложения пользователю не передаются.

Если старая версия Agent уже работает, сохранить её пользовательскую конфигурацию, адрес App, публичный CA и установщик предыдущей версии. Завершить Agent штатно через его интерфейс перед обновлением. Не удалять пользовательские workflow/данные.

## 2. Проверить установщик

В одном каталоге должны быть `ProdCastAgent-Setup-v0.2.exe` и `SHA256SUMS` из доверенного v0.2. В PowerShell:

```powershell
Set-Location 'C:\Install\prodcast-v0.2'
$installer = 'ProdCastAgent-Setup-v0.2.exe'
$line = Get-Content .\SHA256SUMS | Where-Object { ($_ -split '\s+',2)[1] -eq $installer }
if (@($line).Count -ne 1) { throw 'Нет однозначного checksum Agent' }
$expected = ($line -split '\s+',2)[0]
if ((Get-FileHash -LiteralPath $installer -Algorithm SHA256).Hash -ne $expected) { throw 'Agent checksum mismatch' }
Get-AuthenticodeSignature -LiteralPath $installer | Select-Object Status
```

Ожидаемый SHA256: `36b2c34bfece02f770d17736eeaabadc10fedcc3c8087f65b2a6e299089965b2`. Установщик Agent **не имеет Authenticode-подписи**; ожидается `NotSigned`. Если политика площадки требует подписанное ПО, эта версия не удовлетворяет этому требованию: администратору нужен согласованный способ допуска либо отдельно подписанный дистрибутив. Не отключать защиту Windows в инструкции или автоматически.

## 3. Установить и настроить подключение

1. Запустить проверенный EXE интерактивно под будущим пользователем Agent и пройти мастер per-user установки.
2. Запустить Agent, открыть **Connection Settings**.
3. Указать App API URL `https://<реальное-имя-App>/api`, например `https://prodcast-app-01.example.internal/api` после замены документационного имени реальным.
4. Сохранить проверку TLS включённой. Если runtime требует отдельный CA bundle, выбрать выданный администратором публичный PEM/CRT.
5. Сохранить подключение, проверить статус готовности. Выполнять действия через авторизованный App под пользователем с разрешением локального запуска (`workflow_executor` или предусмотренная роль администратора).

Нельзя подставлять License bootstrap token, `MEDIA_DOWNLOAD_API_KEY`, signing key или серверный JWT вместо пользовательской авторизации. Agent должен слушать loopback, обычно `127.0.0.1:9000`; не публиковать его порт в LAN/Интернет.

## 4. Проверить работу

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:9000/healthz'
Invoke-RestMethod -Uri 'http://127.0.0.1:9000/readyz'
Get-NetTCPConnection -State Listen -LocalPort 9000 | Select-Object LocalAddress,LocalPort,OwningProcess
```

Ожидаются успешные health/readiness и loopback listener. Затем в App выполнить один разрешённый локальный notebook `print(6 * 7)` и простую блоковую схему: получить 42 и читаемые шаги выполнения. Проверить, что запрос исполнения без пользовательской авторизации отвергается. При ошибке TLS исправить доверие CA/имя сервера; при 401/403 проверить пользовательскую сессию и роль.

## 5. Зафиксировать установку и откат

В журнал записать user/device identifier по политике площадки, installer SHA256, внутреннюю версию, App URL, CA fingerprint, результаты notebook/blocks. Для отката завершить Agent, восстановить предыдущую совместимую версию из проверенного установщика и сохранённые пользовательские настройки. Согласовать App/Agent как пару: v0.2 сохраняет ту же пару бинарных файлов, что v0.1.
