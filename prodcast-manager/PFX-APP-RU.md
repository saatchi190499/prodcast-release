# Portable Manager 0.1.10

В новой версии данные доступа сохраняются автоматически в data/sites рядом с EXE. Вместо «Импортировать в vault» используется кнопка «Сохранить сертификат». Отдельный пароль хранилища нужен только при импорте старой площадки; пароль самого PFX по-прежнему требуется. Далее техническое описание механизма импорта и применения, совместимого с 0.1.7+.

# Сертификат организации для ProdCast App — Manager 0.1.7

Manager принимает PFX/P12 напрямую. Извлекать CRT и PEM вручную не требуется. Пароль PFX используется для расшифровки в памяти; Manager не сохраняет этот пароль. Серверный ключ хранится на ПК администратора внутри зашифрованного vault, а на App VM — в защищённом файле, необходимом nginx. Приватный ключ CA организации не нужен.

## Что получить от администратора клиента

1. Адрес сайта, например `https://prodcast` или `https://prodcast.company.local`.
2. PFX/P12 с серверным сертификатом **и приватным ключом**; пароль передать по принятому защищённому каналу.
3. Полную цепочку CA до корня. Обычно она включена в PFX. Если её там нет, нужен отдельный PEM-файл с промежуточными и корневым сертификатами (без приватных ключей CA).
4. Подтверждение, что это DNS-имя указывает на IP App с клиентских ПК, а браузеры пользователей доверяют CA организации. Manager не меняет DNS и хранилища доверия клиентских ПК.

В сертификате имя сайта должно входить в SAN, сертификат должен действовать и допускать TLS Server Authentication. Поддерживаются RSA от 2048 бит и EC от 256 бит, обычные DNS SAN и wildcard одного уровня. Например, `*.company.local` подходит для `prodcast.company.local`, но не для `prodcast` и не для `a.prodcast.company.local`. Проверяются подписи и ограничения полной цепочки. Проверку отзыва через CRL/OCSP Manager не выполняет; этот вопрос остаётся в политике PKI клиента.

## Импорт в GUI

1. Сохранить `ProdCast-Manager.exe` в постоянную папку с правом записи и запустить его.
2. Открыть исходный `site.json` и исходный каталог площадки. Для существующей установки сохранить её IP, ID и **внутренний HTTPS адрес App** на вкладке «Площадка». Не менять его на имя из PFX. Для новой установки использовать здесь `https://IP_App`.
3. На вкладке «Установка и обновление» ввести пароль **существующего vault**. Он отличается от пароля PFX. Нажать «Открыть / сохранить vault».
4. Открыть вкладку **«Сертификат App»**. Указать адрес сайта клиента, выбрать PFX/P12 и ввести пароль PFX. При необходимости выбрать дополнительную цепочку CA в PEM.
5. Нажать **«Проверить PFX»**. Проверить показанные адрес, издателя, срок действия и SHA256. Сверить корневой CA с администратором клиента по доверенному каналу. Эта проверка не подключается к серверам и ничего не сохраняет в vault.
6. Нажать **«Импортировать в vault»**. После сохранения поле пароля PFX очищается. Перед заменой создаётся зашифрованная копия прежнего vault в `history`. Исходный PFX, его путь и пароль не сохраняются в `site.json`.

Если файл не содержит корневого CA, выбрать дополнительный PEM-файл. Если отсутствует приватный ключ, запросить у клиента новый экспорт PFX с ключом. Неправильный пароль, неподходящее имя, истёкший сертификат, неподходящее назначение и неверная цепочка блокируют импорт.

## Применение к уже установленному App

1. Выделить окно обслуживания: операция перезапускает gateway и восемь веб-сервисов App. На время перезапуска сайт может быть недоступен.
2. На вкладке «Сертификат App» нажать **«Применить сертификат на App»**. Релиз ZIP для этой операции не нужен. Manager подключается по SSH только к App и проверяет принадлежность установки исходному vault.
3. Проверить адрес VM в окне запуска и подтвердить операцию. Предыдущие конфигурационные файлы и сертификат сохраняются на App в `/var/lib/prodcast-manager/app-tls-backups/<operation>/` с ограниченными правами.
4. Дождаться успешного сообщения. До перезапуска выполняется `nginx -t` с реальным шаблоном установленного gateway. Затем Manager проверяет HTTPS `/readyz` по имени клиента с проверкой CA и имени сертификата, а также прежний внутренний HTTPS адрес. Для новой проверки соединение направляется прямо на IP App с корректными SNI и Host: исправность DNS пользователя этим не подтверждается.
5. С рабочего ПК клиента открыть именно указанный доменный адрес, например `https://prodcast.company.local/login`. Проверить сертификат в браузере, вход и обычную работу приложения.

При ошибке серверная процедура пытается восстановить предыдущие файлы и запустить веб-сервисы с прежней конфигурацией. Ошибка восстановления сообщается отдельно. При обрыве SSH результат может быть неизвестен: сохранить vault и журналы, устранить причину и повторить **ту же** операцию «Применить сертификат на App». Не импортировать другой PFX и не запускать обновление, пока эта операция не завершена.

Логи GUI и полученная диагностика сервера сохраняются в `logs` рядом с EXE. Локальный журнал операции — `app-tls-journal.json` в каталоге площадки. Серверный журнал — `/var/lib/prodcast-manager/operation.log` на App VM. Пароли и приватные ключи удаляются из локальных диагностических сообщений.

## Первая установка, обновления и продление

### Доверие на рабочем ПК

PFX с приватным ключом импортируется в Manager для установки на App. Для доверия браузера на клиентском ПК нужен публичный корневой сертификат выпустившего CA в хранилище Windows «Доверенные корневые центры сертификации» (или доверие, установленное корпоративной политикой). Импорт одного серверного PFX в «Личное» не заменяет доверия к CA. Приватный ключ сайта для просмотра сайта на ПК не требуется.

Открывайте HTTPS по точному DNS-имени из сертификата. Для созданного локального комплекта это `https://prodcast-app-01.btl.nrg/login`, корневой сертификат — `ProdCast-Local-CA.cer`. Доверие к этому CA не переносится автоматически на другой ПК. Адрес по IP обслуживается отдельным внутренним сертификатом Manager.

Если браузер продолжает показывать предупреждение, зафиксируйте точный URL и код ошибки сертификата. Сравните сертификат, выданный сервером, с импортированным PFX, проверьте SAN, срок действия и хранилище доверенного CA именно того пользователя и ПК, где открыт браузер. Наличие PFX в vault само по себе не означает, что он уже применён к App.

Для новой площадки сначала импортировать PFX в vault, затем выполнить обычную установку. Для обновлений использовать тот же vault: клиентский сертификат применяется из него автоматически. Встроенный CA Manager и сертификаты DB и AI не заменяются сертификатом клиента.

App обслуживает два HTTPS-имени на одном порту 443: исходный внутренний адрес с сертификатом Manager и адрес клиента с его сертификатом. Workers сохраняют внутренний адрес и доверие прежнему CA. HTTP-вход перенаправляется на доменное имя клиента. Backend разрешает оба адреса, а публичным адресом сайта становится адрес клиента. Для этого клиентский адрес должен отличаться от исходного внутреннего HTTPS адреса App. Перенос уже существующего внутреннего адреса площадки эта функция не выполняет.

Автоматическое продление сертификатов корпоративного CA не реализовано. До истечения срока получить новый PFX, импортировать его и повторить «Применить сертификат на App». Старые версии Manager до 0.1.7 не поддерживают этот режим — не использовать их для обновления площадки после импорта.

## CLI

Сначала импорт (оба пароля запрашиваются интерактивно и не передаются аргументами командной строки):

```powershell
.\prodcast-manager-cli.exe import-pfx --site 'C:\ProdCastSite\site.json' --pfx 'C:\Certificates\prodcast.pfx' --app-url 'https://prodcast.company.local'
```

Если нужна отдельная цепочка, добавить `--ca-chain 'C:\Certificates\chain.pem'`.

Применение к установленному App в согласованное окно обслуживания:

```powershell
.\prodcast-manager-cli.exe app-tls --site 'C:\ProdCastSite\site.json' --yes
```

## Область проверки версии 0.1.7

Импорт, проверка ключа и цепочки, шифрование vault, GUI, сохранение при инициализации/обновлении, ограничение передачи ключа ролью App, повтор операции и восстановление файлов проверяются автоматическими тестами. Отдельная локальная интеграционная проверка на настоящем nginx 1.30.5 для Windows подтверждает выбор двух сертификатов по SNI, строгую TLS-проверку и HTTP redirect на синтетических сертификатах.

Сертификат клиента не предоставлен в этой задаче. Проверка его фактической цепочки, политики доверия и DNS, применение на Linux App VM и проверка браузеров клиента ещё не выполнены. Локальная проверка nginx не заменяет эти проверки в сети клиента.
