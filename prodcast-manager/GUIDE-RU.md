# ProdCast Manager 0.6 — руководство

## Запуск и состав релиза

Распакуйте весь ZIP в доступную для записи папку. Запустите `ProdCast-Manager.exe`; папка `_internal` должна оставаться рядом. Python на компьютере оператора устанавливать не требуется. Для командной строки используйте `prodcast-manager-cli.exe`.

В комплект входят исходники `source.zip`, документация RU/EN, пример `site.example.json`, контрольные суммы `SHA256SUMS` и отчёты `VALIDATION.json`, `TEST-RESULTS.xml`. Пример содержит демонстрационные адреса, которые нужно заменить.

Версия Manager и версия устанавливаемого ProdCast — разные вещи. Manager 0.6 не означает, что нужно выбирать релиз ProdCast 0.6.

## Профиль и доступ

Для существующей установки откройте её исходный `site.json` вместе с оригинальным хранилищем доступа. Переносите всю папку профиля, включая `secrets.json`, `secrets.key`, SSH-ключи и журналы. Не создавайте новый профиль для уже установленной площадки. Перед изменениями сохраните резервную копию профиля.

Папка профиля и её резервные копии содержат секреты. Не размещайте их в общедоступных каталогах и не отправляйте вместе с логами. Подтверждайте SSH-отпечатки через доверенную консоль VM.

## Выбор действия

| Задача | Действие |
| --- | --- |
| Первичная установка на подготовленные VM без прежнего ProdCast | «Установить» |
| Обновление установленной площадки | «Обновить», в согласованное окно обслуживания |
| Добавление новой Windows VM как Worker | «Добавить Workers…» |
| Сохранение введённых настроек | «Сохранить конфигурацию»; это не установка |

## Добавление Worker

1. Откройте установленный профиль и выберите полный пакет **точного установленного релиза ProdCast**, с его доверенным SHA-256 манифеста.
2. На вкладке «Серверы» увеличьте количество Workers. Поддерживается суммарно до 16, если выбранный пакет Worker допускает это количество.
3. Укажите IP новой VM, SSH-доступ и подтверждённый отпечаток. Не меняйте адреса прежних VM и остальные настройки площадки.
4. Нажмите «Добавить Workers…» и подтвердите список новых серверов. Отдельно нажимать «Установить» не нужно: строка `worker3: install` в журнале — внутренний шаг добавления.
5. Дождитесь `Workers added: worker3` (или списка добавленных ролей). После установки проверьте выполнение реального задания и работу после перезагрузки в согласованное время.

App, прежние Workers и контейнеры БД этой операцией не перезапускаются; новые доступы добавляются в БД. Идентичность площадки и старые секреты сохраняются. Удаление или перенумерация Workers не поддерживаются. После расширения используйте обновлённый профиль и Manager 0.6 или новее.

Если операция прервалась после начала изменений, повторите «Добавить Workers…» с тем же релизом и адресами. Не удаляйте журнал или секреты. Отказ только на предварительной проверке позволяет исправить параметры новых VM. Не переносите профиль во время незавершённой операции.

## VM, созданная из бэкапа другого Worker

Смена IP и имени Windows не удаляет старую роль, службу и секреты ProdCast. Клон с `role=worker2` и службой `ProdCastWorker02` не является чистой VM для Worker3; Manager откажется автоматически переиспользовать такую установку.

Проверяйте имя, IP, службы и роль через консоль именно клона. Используйте чистую VM либо выполняйте отдельную согласованную очистку клона с проверкой его адреса и принадлежности файлов. Не меняйте роль вручную в JSON и не запускайте общую очистку площадки ради одного клона. Скопированная работающая служба может подключаться к общей очереди под прежними учётными данными.

## Предупреждение об очистке временных файлов

Если после успешных `verify`, `commit`, `db: workers-commit` и `Workers added` появляется `Could not clean a temporary staging directory`, добавление уже завершено. Повторная установка и очистка установленного Worker не требуются.

Это известное ограничение диагностики 0.6: предупреждение не сообщает VM и причину. Возможный источник — созданные от root временные файлы на Linux, которые затем пытается удалить обычный SSH-пользователь. Без дополнительной проверки это не подтверждённая причина конкретного случая.

Временные папки создаются под `C:\ProgramData\ProdCastManager\inbox` на Windows и `/var/tmp/prodcast-manager-<идентификатор>` на Linux. Они могут содержать секреты. Удалять следует только точно установленную папку завершённой операции после проверки VM, отсутствия текущей операции и путей. Не удаляйте весь `ProdCastManager`, `Managed` или профиль ради этого предупреждения. Исправление механизма очистки в эту сборку документации не включено.

## Ollama components

Можно выбрать Ollama ZIP предыдущего релиза, если оба внутренних файла совпадают по SHA-256 и размеру с доверенным манифестом выбранного ProdCast. Имя ZIP, timestamps, способ ZIP-сжатия и имена внутренних файлов могут отличаться. Изменённое содержимое и небезопасные архивы отклоняются. Модель AI проверяется отдельно. Реальный ZIP Ollama 0.4 проверен с манифестом ProdCast 0.5.0.
